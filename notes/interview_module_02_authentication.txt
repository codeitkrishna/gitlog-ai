Must Know First

1. What authentication method does your project use?
  Simple answer
    GitLog AI uses GitHub OAuth through Supabase Auth. The user signs in with GitHub, Supabase creates the application session, and the app also stores the GitHub provider token so it can call GitHub APIs on the user’s behalf.

2. What is the most important auth concept in this project?
  Must know deeply
    The most important concept is that there are really two different auth-related tokens involved.

  Good answer
    The first is the Supabase session token, which proves the user is logged into my app.
    The second is the GitHub provider token, which lets my app call GitHub APIs for that user.
    These two tokens solve different problems. One is app authentication. The other is third-party API authorization.

3. Authentication vs authorization in simple words
  Simple answer
    Authentication means proving who the user is.
    Authorization means deciding what the user is allowed to do.
    In GitLog AI, Supabase session auth proves the user is logged in, and the stored GitHub token authorizes GitHub API access for that user’s repositories and commits.

4. End-to-end auth flow in one short explanation
  Simple answer
    The user clicks GitHub login on the client. Supabase starts the OAuth flow. GitHub redirects back to my callback route with a code. Supabase exchanges that code for a session. Then I store the GitHub provider token in my database for later GitHub API calls. After that, middleware and server-side auth checks protect the rest of the app.

5. Why this module is important in interviews
  Simple answer
    Because it touches frontend, backend, security, OAuth, cookies, middleware, database access, and third-party integrations. It is one of the best modules to test whether someone actually understands full-stack product development.

Section 1: Product-level understanding

1. Walk me through your login flow from button click to protected dashboard.
  Answer Brief
    In GitLog AI, the login button is on a client-side page because it needs browser interaction. When the user clicks "Continue with GitHub", I call Supabase Auth with GitHub as the OAuth provider. GitHub redirects back to my callback route with an auth code. On the server, I exchange that code for a Supabase session. After that, I store the GitHub provider token in my database, because I need it later for Octokit calls. Once the session is established, the user is redirected to the dashboard, and middleware plus server-side checks protect private routes.

2. Why did you choose GitHub OAuth for this project?
  Answer Brief
    Because the product works on top of GitHub repositories and commits. GitHub is the natural identity provider here, and the user already expects to connect their GitHub account. It also reduces friction because they do not have to create a separate username and password for my app.

3. Why did you use Supabase Auth instead of implementing OAuth manually?
  Answer Brief
    OAuth has a lot of complexity around redirects, state, session handling, refresh behavior, and secure cookie handling. Supabase abstracts most of that safely and gives me a clean auth system for both client and server use. That let me focus on product logic instead of rebuilding auth infrastructure.

4. What is the difference between "Login with GitHub" and "Access GitHub APIs" in your app?
  Answer Brief
    They are related, but not the same thing. "Login with GitHub" is how the user signs into GitLog AI. "Access GitHub APIs" is what my app does after login, using the GitHub provider token. The first gives me an app session. The second gives me repository access.

Section 2: OAuth basics

5. Explain OAuth in simple words using your project.
  Must know deeply
    This is one of the highest-value answers in the auth module.

  Good answer
    OAuth is a way for my app to ask another platform for limited access without handling the user’s password directly.
    In GitLog AI, the other platform is GitHub. The user clicks login, GitHub authenticates the user, and then GitHub redirects back with a temporary code. My backend exchanges that code for session information and a provider token. That way, my app never handles the GitHub password itself, but it still gets permission to access repositories based on the approved scopes.

  Good speaking structure
    User starts login
    GitHub authenticates
    GitHub redirects back with code
    Backend exchanges code
    App receives session and provider token
    User is now logged in and GitHub data can be fetched

6. What is the authorization code in your callback flow?
  Answer Brief
    It is a temporary code returned by GitHub after successful OAuth login. My callback route receives that code and hands it to Supabase to exchange for a usable session. I do not use the code directly for API access.

7. Why is your callback route a server route and not a client page?
  Answer Brief
    Because the callback is part of the secure OAuth exchange flow. It receives the redirect from GitHub and is the right place to exchange the code for a session on the server. It also lets me store the provider token right after the exchange before redirecting the user deeper into the app.

8. Why does the login action need to start on the client?
  Answer Brief
    Because it starts from a user click in the browser. The client needs to trigger the OAuth redirect and manage the login button state, like disabling the button and showing a loading state while the redirect is being initiated.

9. What are scopes, and what scopes did you ask for?
  Answer Brief
    Scopes define what permissions the app is requesting from the provider. In my project, I request repository access and basic profile access because I need to read repositories, commits, tags, and basic GitHub identity information. Good practice is to ask only for the minimum scopes needed.

10. Why is least privilege important in OAuth?
  Answer Brief
    Because access tokens are powerful. If the app asks for more permissions than it needs, that increases risk unnecessarily. Least privilege means I request only the minimum permissions required for the product to work.

Section 3: Supabase session vs GitHub provider token

11. Explain the two-token model in your project.
  Must know deeply
    This is probably the most important answer in the whole auth module.

  Good answer
    After OAuth completes, I care about two different pieces of auth state.
    The Supabase session represents login state for GitLog AI itself. It is what I check in middleware, server pages, and API routes to know whether the user is authenticated in my app.
    The GitHub provider token is different. I store it in the database and use it only when I need to call GitHub APIs through Octokit.
    So the Supabase session answers, "Is this user logged into my app?"
    The GitHub token answers, "Can my app access GitHub data for this user?"

12. Why can’t you use only the Supabase session token to call GitHub APIs?
  Answer Brief
    Because the Supabase session token is for my app’s auth system, not for GitHub. GitHub APIs need a GitHub-issued token with the right scopes. The Supabase session proves identity inside my app, but it does not replace the provider token.

13. Why store the provider token in the database at all?
  Answer Brief
    Because later API routes need to fetch repositories, tags, and commits for the user. Those routes run on the server and need the GitHub token to build an authenticated Octokit client. Storing it in the database lets the app retrieve it when needed after login.

14. What would break if the provider token was not stored?
  Answer Brief
    The user could still be logged into my app through Supabase, but repository and commit fetching would fail because my GitHub API routes would have no token to use. So the app session would exist, but GitHub integration would not work.

15. Is storing a provider token in the database a safe idea?
  Answer Brief
    It can be acceptable if done carefully, but it has security implications. It should be protected by row-level security, ideally encrypted or managed more securely, and never exposed to the client. In my project, I protect it with per-user access controls through RLS, but I would still call this an area where security can be strengthened further.

Section 4: Middleware and route protection

16. What is middleware doing in your auth architecture?
  Answer Brief
    Middleware checks session state early on each request, refreshes cookies when needed, and redirects unauthenticated users away from protected routes. It also redirects authenticated users away from the login page so they are not sent through an unnecessary auth screen again.

17. Why use middleware if some pages also check auth and redirect?
  Answer Brief
    Middleware is the first line of protection and helps enforce rules at the request level. Page-level checks are still useful as defense in depth. If middleware changes later or a route is reached in a different way, server-page checks still protect the page.

18. What is the difference between middleware protection and API route checks?
  Answer Brief
    Middleware protects route access at the request-routing level, mainly for page navigation. API route checks protect backend endpoints directly. Even if a page is protected, I still need API routes to verify the user because someone could call the endpoint directly.

19. Why is relying only on frontend route guards a bad idea?
  Answer Brief
    Because frontend checks can be bypassed. Real protection must happen on the server. Client-side hiding or redirect logic can improve UX, but it is not a security boundary.

20. What is a protected route in your project?
  Answer Brief
    A protected route is any route that should only be accessible to authenticated users, such as the dashboard, generator pages, and history pages. In my project, middleware checks these and redirects unauthenticated users to login.

Section 5: Client-side and server-side auth clients

21. Why do you have both a browser Supabase client and a server Supabase client?
  Must know deeply
    This is a very common and important interview topic.

  Good answer
    Because auth responsibilities are different on the client and server.
    On the client, I need a browser-side Supabase client to start OAuth login, handle logout from user interactions, and listen to auth state changes if needed.
    On the server, I need a server-side client that can read request cookies and understand session state during rendering or inside route handlers.
    So I separated them into `lib/supabase/client.ts` and `lib/supabase/server.ts`.

22. What kind of work belongs in the browser auth client?
  Answer Brief
    Starting login, signing out, listening to auth state changes, and any auth action initiated directly by the user in the browser.

23. What kind of work belongs in the server auth client?
  Answer Brief
    Reading session state during SSR, checking authentication in API routes, exchanging the OAuth code for a session in the callback, and accessing protected server-side logic tied to the current user.

24. Why is the login page a Client Component?
  Answer Brief
    Because it needs user interaction, local loading state, and a browser-side auth call to begin the GitHub OAuth redirect. Those are client-side responsibilities.

25. Why are dashboard and generator pages still checking auth on the server?
  Answer Brief
    Because those pages are protected and should not render for unauthenticated users. Server-side checks make sure unauthorized access is blocked before the page is rendered.

Section 6: Database and RLS discussion

26. Why do you use a `user_tokens` table?
  Answer Brief
    The `user_tokens` table stores the GitHub provider access token for each authenticated user so my backend routes can later call GitHub APIs for that specific user.

27. Why is row-level security relevant here?
  Must know deeply
    This is very useful because your resume already mentions RLS and interviewers will likely ask about it.

  Good answer
    Row-level security helps enforce multi-tenant isolation at the database layer. In my project, each user should only be able to access their own stored token and data. RLS policies tied to `auth.uid()` help make sure one user cannot read or modify another user’s token row.
    This is important because application-level checks are not enough by themselves. Database-level rules add another layer of protection.

28. What problem does `auth.uid() = user_id` solve?
  Answer Brief
    It ensures that the current authenticated user can only operate on rows that belong to their own user ID. That is the core rule that gives per-user data isolation.

29. Why is RLS especially useful in multi-user SaaS-style apps?
  Answer Brief
    Because many users share the same tables, so tenant separation becomes critical. RLS gives protection at the database level instead of trusting every part of the application code to always filter correctly.

30. Is RLS alone enough for full security?
  Answer Brief
    No. It is important, but it is only one layer. I still need secure auth handling, proper route checks, safe token handling, good logging practices, and careful backend logic. Good security is layered.

Section 7: Security tradeoffs and weaknesses

31. If I ask you to critique your own auth implementation honestly, what would you say?
  Must know deeply
    This is a high-quality interview answer if you speak honestly and clearly.

  Good answer
    I would say the overall flow is correct, but there are a few places to improve.
    First, sensitive provider token values should not be logged.
    Second, storing third-party access tokens in plain text is functional but not ideal from a security point of view.
    Third, token lifecycle handling can be improved, especially around rotation, expiry awareness, and cleanup.
    So I would describe the current implementation as good for project functionality, but not the final version I would want for a production system with stronger security requirements.

32. Why is logging provider tokens a bad idea?
  Answer Brief
    Because logs often get copied, stored, and viewed in many places. If a token appears in logs, it increases the risk of accidental exposure. Sensitive tokens should be masked or never logged at all.

33. What are better options than storing raw access tokens directly?
  Answer Brief
    Better options include encryption at rest, tighter secret handling, shorter token lifetime strategies, and more controlled backend storage patterns. The exact solution depends on the infrastructure, but the general principle is to reduce exposure of reusable credentials.

34. What other security concerns should you be aware of in OAuth integrations?
  Answer Brief
    Scope minimization, secure callback handling, token exposure in logs, replay concerns, session fixation concerns, protecting server routes, and not exposing provider tokens to the browser unnecessarily.

35. Does logout automatically remove the provider token from your database?
  Answer Brief
    In my current implementation, logout signs the user out of the app session, but it does not remove the stored GitHub token row. That is acceptable for basic functionality because access is still protected by auth and RLS, but it is worth discussing as a lifecycle improvement if stricter token hygiene is required.

36. How would you improve token lifecycle management?
  Answer Brief
    I would think about token expiry handling, refresh behavior if supported, removing stale tokens, re-authentication when tokens are invalid, and clearer recovery flows when GitHub access has expired or been revoked.

Section 8: Error handling and resilience

37. What are common auth failure cases in your project?
  Answer Brief
    OAuth exchange can fail, provider token storage can fail, session cookies might be missing or expired, login can be cancelled, the token may not exist when an API route later needs it, or the user may have revoked GitHub access.

38. How do you handle callback failure today?
  Answer Brief
    If the OAuth code exchange fails, I redirect the user back to login with an auth error. That keeps the flow simple and gives the user a path to retry.

39. What happens if the app session exists but the GitHub token is missing?
  Answer Brief
    Then the user is authenticated in my app, but GitHub-related functionality breaks. In my routes that fetch repositories or commits, I return an error telling the user the GitHub token was not found and that they may need to log in again.

40. Why is that an important interview talking point?
  Answer Brief
    Because it shows that auth is not only about logging in successfully. It is also about handling partial failure states where one piece of auth is valid but another integration dependency is missing.

41. What would you improve in the login UX if there is an auth error?
  Answer Brief
    I would make the error handling more user-friendly by showing clear in-page messages instead of relying on generic alerts or console logs. I would also explain recovery steps, like retrying login or reconnecting GitHub.

Section 9: Logout and auth state changes

42. How does logout work in your project?
  Answer Brief
    Logout is triggered from the user menu on the client. It calls Supabase signOut using the browser client, then navigates the user back to the home page and refreshes the router so the UI reflects the logged-out state.

43. Why is router refresh useful after logout?
  Answer Brief
    Because some parts of the app are server-rendered based on auth state. A router refresh helps make sure the new server-rendered UI reflects that the user is now logged out.

44. How would you explain auth state changes on the client?
  Answer Brief
    The browser can subscribe to auth state changes so that UI can react when login or logout happens. In my project, I also have a `useUser` hook pattern that can listen for those changes if a client component needs it.

45. Is listening to auth state changes always necessary?
  Answer Brief
    No. It is helpful for interactive client components, but if the flow is mostly server-rendered and navigation-based, not every component needs a live auth subscription.

Section 10: Authorization with GitHub and Octokit

46. Once the user is logged in, how does the app access GitHub data?
  Answer Brief
    Protected API routes first check the Supabase session to confirm the user is authenticated. Then they query the user’s stored GitHub access token from the database. With that token, they create an authenticated Octokit client and fetch repositories, tags, or commits from GitHub.

47. Why is this a good full-stack interview point?
  Answer Brief
    Because it shows that I understand the whole chain: frontend login, backend session validation, database token lookup, and third-party API integration. It is a real end-to-end workflow, not just a UI-only auth example.

48. Why do your API routes still check `supabase.auth.getUser()` even after login?
  Answer Brief
    Because every API route must protect itself. Even if the user came from a protected page, the endpoint can still be called directly, so it needs its own auth verification.

49. What would happen if you skipped the server-side auth check and only looked up the GitHub token?
  Answer Brief
    That would be unsafe. The route should first confirm the caller is an authenticated user, then scope the token lookup to that user’s ID. Otherwise, it weakens the security model.

Section 11: Realistic comparison and reasoning questions

50. Why not just keep everything auth-related on the client?
  Answer Brief
    Because security and SSR correctness need server involvement. The client is fine for starting login and handling logout clicks, but route protection, session-aware rendering, callback exchange, and secure API authorization checks should happen on the server.

51. Why not use JWT manually and skip Supabase Auth?
  Answer Brief
    I could, but I would be rebuilding a lot of auth infrastructure myself. Supabase already gives me secure session handling, OAuth integration, and server-client compatibility. For a project like this, that was a better engineering tradeoff.

52. Why not store the GitHub token in localStorage and avoid the database?
  Answer Brief
    That would be a worse security choice because localStorage is accessible in the browser and is a common target for token exposure. I wanted the provider token to stay on the backend side so server routes can use it without exposing it to the client.

53. If an interviewer asks whether your auth is "production ready", how do you answer honestly?
  Answer Brief
    I would say the architecture is solid and the flow is correct, but I would not oversell it as perfect production security. I would specifically mention improvements around sensitive logging, token storage hardening, and more polished user-facing error handling.

Section 12: Testing and debugging

54. How would you test this auth module?
  Answer Brief
    I would test:
    login initiation from the client
    successful callback exchange
    redirect to dashboard after login
    redirect to login for protected routes when unauthenticated
    redirect away from login when already authenticated
    logout flow
    missing token behavior in repository-fetching routes
    route-level unauthorized responses from APIs

55. What is a realistic bug in this module?
  Answer Brief
    One realistic bug is that the user is logged into the app but the GitHub token was not stored properly, so repository fetching fails later. Another is session refresh issues causing inconsistent protected-route behavior. Another is poor handling of revoked GitHub access.

56. If a user says, "I can log in, but I can’t fetch repos," what is your debugging path?
  Must know deeply
    This is a great practical debugging answer.

  Good answer
    I would debug the flow in layers.
    First, confirm the Supabase session exists and the user is authenticated.
    Second, confirm the callback exchange succeeded.
    Third, check whether the GitHub provider token was stored in `user_tokens`.
    Fourth, verify the token lookup query in the repos API route.
    Fifth, verify GitHub scopes and whether the token still works with Octokit.
    This layered approach is better than guessing because the failure could be in session auth, callback handling, token persistence, or GitHub access itself.

57. What logs are useful, and what logs are dangerous?
  Answer Brief
    Useful logs are flow events, error categories, user-safe identifiers, and success or failure points. Dangerous logs are raw provider tokens, secret values, full session details, and anything that can be reused as a credential.

Section 13: Strong answers to practice

1. Explain your auth architecture in one strong answer
  Strong study answer
    GitLog AI uses GitHub OAuth through Supabase Auth. The login starts in a client component because it is a browser interaction. GitHub redirects to my callback route, where Supabase exchanges the OAuth code for a session. After that, I store the GitHub provider token in a protected database table so backend routes can later call GitHub APIs through Octokit. Middleware protects private routes and helps refresh session state, while API routes also verify the user independently. So the architecture separates app authentication from GitHub API authorization while keeping both connected cleanly.

2. Explain session token vs provider token in one strong answer
  Strong study answer
    In my project, the Supabase session token tells me whether the user is logged into GitLog AI. The GitHub provider token is different: it lets my backend call GitHub APIs on behalf of that user. I need both because one handles app login and the other handles GitHub access. Treating them as separate concerns helped me design the auth flow more clearly.

3. Explain why middleware exists in one strong answer
  Strong study answer
    Middleware lets me apply authentication rules early in the request lifecycle. It refreshes session state when needed and redirects users away from pages they should not access, like dashboard or generator routes when unauthenticated. That improves both security and user flow because the redirect happens before the protected page renders.

4. Explain the biggest security improvement you would make
  Strong study answer
    The first improvement I would make is removing sensitive token logging and hardening provider token storage. The current architecture is functionally correct, but reusable third-party tokens should be treated very carefully. I would strengthen token handling, improve error messaging, and make the flow more production-grade from a security perspective.
