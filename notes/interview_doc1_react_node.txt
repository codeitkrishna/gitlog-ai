  It is not tied closely to one project.

Part 1: React

1. What React really is
  React is a library for building user interfaces using components.
  Its main idea is that UI should be a function of state.
  When state changes, React updates the DOM efficiently instead of you manually selecting elements and changing them.

  Short answer
    React is a component-based UI library that lets you build declarative user interfaces.

  Better answer
    React lets developers describe what the UI should look like for a given state, and React handles updating the real DOM efficiently when the state changes.

2. Declarative vs imperative programming
  Declarative UI means you describe the desired result.
  Imperative UI means you manually write each DOM update step.

  Example idea
    Declarative:
      "If the user is logged in, show dashboard button."
    Imperative:
      "Find the button element, change its text, add a class, attach a click handler."

  Why interviewers ask this
    They want to know whether you understand React as a UI model, not just syntax.

3. Components
  A component is a reusable piece of UI and logic.
  React applications are built by composing smaller components into larger ones.

  Types of components you should know
    presentational components
    container components
    controlled components
    higher-order components
    custom-hook-based logic components

  Frequent question
    What makes a good React component?

  Good answer
    A good component has a clear responsibility, clean props, predictable behavior, and minimal unnecessary state.

4. JSX
  JSX is syntax that looks like HTML but compiles into JavaScript function calls.
  It is not HTML.
  It lets you write UI structure in a more readable way.

  Important things to remember
    JSX expressions go inside curly braces
    `className` is used instead of `class`
    components must return one parent element or a fragment
    JavaScript logic can be embedded inside JSX carefully

5. Props
  Props are inputs passed from parent to child components.
  They make components configurable and reusable.

  Important points
    props are read-only
    child components should not mutate props
    props help make UI predictable

  Common question
    What is the difference between props and state?

  Good answer
    Props come from the parent and are read-only from the child’s perspective.
    State is owned and managed by the component itself.

6. State
  State is data that changes over time and affects rendering.
  In React, state updates cause re-renders.

  Important points
    state should represent UI data that can change
    do not put everything into state
    derived values often do not need separate state
    state updates are asynchronous from the developer’s perspective

  Common mistake
    storing redundant state that can be derived from existing state or props

7. Lifting state up
  When two or more components need the same data, move that state to their nearest common parent.
  Then pass the value and update functions down via props.

  Why this matters
    It creates a single source of truth.
    It reduces inconsistent UI state between sibling components.

  Common interview phrasing
    When should you lift state up?

  Good answer
    When multiple components need to read or update the same state, and keeping separate copies would create synchronization problems.

8. Controlled vs uncontrolled components
  Controlled component
    form value is controlled by React state

  Uncontrolled component
    form value is managed by the DOM itself, usually accessed via refs

  Why controlled components are common
    They make validation, conditional rendering, and dynamic form behavior easier.

  Common question
    When would you use uncontrolled inputs?

  Good answer
    Usually for simpler forms, file inputs, quick prototypes, or integration with non-React code. Controlled inputs are preferred when UI behavior depends heavily on the form state.

9. Event handling in React
  React wraps browser events in a consistent event system.
  Event handlers are passed as functions.

  Important ideas
    do not call the handler immediately in JSX unless intentional
    use arrow functions only when needed
    understand `event.target.value` in form handlers

  Example
    Correct:
      onClick={handleClick}
    Also valid:
      onClick={() => handleClick(id)}

10. Conditional rendering
  React commonly uses:
    if statements outside JSX
    ternary operators
    `&&` short-circuit rendering

  What interviewers care about
    Whether you can structure UI states clearly without making JSX unreadable.

11. Lists and keys
  When rendering a list, React needs a stable `key` for each item.
  Keys help React understand which elements changed between renders.

  Important rule
    Use stable unique IDs when possible.
    Avoid array index as key if the list can reorder, insert, or delete items.

  Common question
    Why are keys important?

  Good answer
    Keys help React identify elements across renders so it can update the UI correctly and avoid state bugs in list items.

12. React rendering basics
  A component re-renders when:
    its state changes
    its props change
    its parent re-renders and React decides this child should also render
    subscribed context changes

  Important clarification
    A re-render does not always mean a real DOM update.
    React first re-runs the component and then compares the result before updating the DOM.

13. Reconciliation and the virtual DOM
  React builds an in-memory representation of UI and compares old and new trees.
  This comparison process is part of reconciliation.

  Important point
    The virtual DOM is not "faster than the real DOM" in a simple magical sense.
    It is useful because it gives React a structured way to decide what actually needs updating.

14. Hooks
  Hooks let function components use state, lifecycle-like behavior, refs, and shared logic.

  Hooks you must know well
    useState
    useEffect
    useRef
    useContext
    useReducer
    useMemo
    useCallback

15. useState
  `useState` stores local component state.

  Important points
    updates trigger re-render
    state updates can use direct values or updater functions
    updater functions are safer when the next state depends on previous state

  Example concept
    setCount(prev => prev + 1)

16. useEffect
  `useEffect` runs side effects after render.

  Common uses
    data fetching
    subscriptions
    timers
    DOM APIs
    cleanup logic

  Important ideas
    dependencies control when effect runs
    cleanup runs before next effect or on unmount
    effects are for side effects, not for pure calculations

  Common mistakes
    missing dependencies
    putting derived calculations into effects unnecessarily
    creating render loops by updating state incorrectly inside an effect

17. useRef
  `useRef` stores mutable values that persist across renders without causing re-render.

  Common uses
    accessing DOM elements
    storing previous values
    storing timer IDs
    avoiding unnecessary re-renders for mutable non-UI data

18. useContext
  `useContext` helps share values across the component tree without prop drilling every level.

  Good use cases
    theme
    auth user
    language
    global UI state

  Important warning
    Overusing context can cause widespread re-renders and harder-to-follow data flow.

19. useReducer
  `useReducer` is useful when state transitions are more complex.
  It is often preferred when:
    state has multiple related fields
    updates depend on action types
    state logic is getting hard to manage with many `useState` calls

20. useMemo and useCallback
  `useMemo` memoizes computed values.
  `useCallback` memoizes functions.

  Important interview point
    Do not use them everywhere automatically.
    Use them when there is a real rerender or expensive-computation reason.

  Good answer
    These hooks are performance tools, not default coding style rules.

21. Custom hooks
  Custom hooks let you reuse logic across components without reusing UI.

  Good use cases
    auth state handling
    data fetching logic
    form logic
    event listeners
    debouncing logic

22. Component lifecycle in function components
  In function components, lifecycle behavior is modeled mainly through render plus hooks.

  Rough mapping
    mount-related logic -> effect with dependency array
    update-related logic -> effect with dependencies
    unmount cleanup -> cleanup function inside effect

23. Forms in React
  Frequently asked topics
    controlled inputs
    validation
    onChange handling
    submit handling
    form libraries vs plain React

  Good answer
    For simple forms, plain controlled inputs are enough.
    For large forms, a library can reduce boilerplate and improve validation handling.

24. State colocation
  State should live as close as possible to where it is needed, but not so low that it becomes duplicated.

  This is the balance:
    too high -> unnecessary rerenders and prop drilling
    too low -> duplicated state and synchronization issues

25. Prop drilling
  Prop drilling means passing props through many layers only so deeper components can use them.

  Solutions
    component composition
    context
    local state restructuring
    state libraries when truly needed

26. Error boundaries
  Error boundaries catch rendering errors in the React tree.
  They do not catch every kind of error, such as async errors in event handlers automatically.

  Good interview point
    Error boundaries improve resilience of the UI, especially in large applications.

27. React performance basics
  Important things interviewers ask
    why rerenders happen
    how to reduce unnecessary rerenders
    memoization
    splitting large components
    virtualization for long lists

  Strong practical answer
    Start by measuring and understanding rerenders before optimizing.

28. React.memo
  `React.memo` memoizes a component and avoids rerender if props are shallow-equal.

  Important warning
    It is useful only when rerenders are actually unnecessary and the props stay stable.

29. Hydration
  Hydration happens when server-rendered HTML becomes interactive in the browser.

  Why it matters
    Server-rendered React must match the client-rendered version.
    If not, hydration mismatches can happen.

  Common causes of hydration mismatch
    rendering time-based values directly
    using browser-only APIs during server render
    using non-deterministic values like random numbers too early

30. Server Components vs Client Components
  In modern React frameworks like Next.js, some components can render on the server while others run in the browser.

  Important idea
    Not everything interactive belongs on the server, and not everything dynamic needs to be a client component.

31. React architecture topics often asked
  You should be comfortable discussing:
    presentational vs container components
    feature-based folder structure
    custom hooks for logic reuse
    state colocation
    when to use context
    when to introduce a global state library

32. When to use a global state library
  Use it when:
    many unrelated parts of the app need the same state
    prop drilling or context becomes hard to manage
    server state and local UI state need clearer separation

  Do not use it just because the project is large.

33. React interview traps
  Be careful with these
    saying every rerender is bad
    saying virtual DOM is always faster
    using `useEffect` for everything
    overusing `useMemo` and `useCallback`
    not understanding controlled components
    confusing props and state

34. Short React revision list
  Make sure you can explain:
    declarative UI
    props vs state
    lifting state up
    controlled vs uncontrolled inputs
    hooks and when to use them
    rerender vs DOM update
    keys in lists
    context
    hydration
    memoization tradeoffs

Part 2: Node.js

1. What Node.js really is
  Node.js is a JavaScript runtime built on Chrome’s V8 engine.
  It lets JavaScript run outside the browser, especially for backend and tooling use cases.

  Short answer
    Node.js is a runtime for running JavaScript on the server.

  Better answer
    Node.js is an event-driven, non-blocking runtime that is well suited for I/O-heavy server applications.

2. Why Node.js became popular
  Key reasons
    same language on frontend and backend
    strong ecosystem
    good fit for network and I/O-heavy workloads
    fast iteration for web apps and APIs

3. Node.js is not the browser
  Important difference
    Node has JavaScript, but not browser APIs like DOM, `window`, or `document`.
    Instead, Node provides server-side APIs like `fs`, `http`, `path`, `process`, and streams.

4. Event-driven architecture
  Node is designed around asynchronous events and callbacks/promises.
  This makes it strong for many concurrent I/O operations such as database calls, API calls, and file reads.

5. The event loop
  The event loop is a key Node concept.
  It manages the execution of asynchronous callbacks and scheduled tasks.

  Interview-safe explanation
    JavaScript in Node runs on a single main thread for application logic, but Node delegates many I/O operations to the system or thread pool, then processes their results via the event loop.

6. Why Node is good for I/O-heavy work
  Because it can handle many waiting operations efficiently.
  While one database query or API call is waiting, Node can continue handling other tasks.

7. Why Node is not ideal for CPU-heavy work by default
  Heavy CPU work blocks the main thread and delays other requests.

  Better answer
    Node is excellent for concurrent I/O, but CPU-heavy computation may need worker threads, separate services, or other architecture choices.

8. Single-threaded does not mean "can do only one thing"
  This is a common confusion.
  JavaScript execution is single-threaded at the main event-loop level, but asynchronous operations can be managed concurrently.

9. Call stack, callback queue, and event loop
  Basic model
    synchronous code goes on the call stack
    async results wait in queues
    event loop pushes ready callbacks when the stack is free

  You do not need to memorize every phase perfectly for beginner interviews, but you should understand the model clearly.

10. Microtasks vs macrotasks
  Microtasks
    promise callbacks
    queueMicrotask

  Macrotasks
    setTimeout
    setInterval
    setImmediate
    I/O callbacks

  Common interview question
    Which runs first, a promise callback or setTimeout?

  Good answer
    Promise microtasks run before the next macrotask like `setTimeout`.

11. CommonJS vs ES modules
  CommonJS
    `require`
    `module.exports`

  ES modules
    `import`
    `export`

  Important point
    Node supports both, but project configuration matters.

12. package.json
  `package.json` defines project metadata, scripts, dependencies, and package behavior.

  Interview-relevant things
    dependencies vs devDependencies
    scripts
    module type
    versioning

13. npm basics
  npm is the package manager ecosystem around Node.

  Know the basics
    installing packages
    semantic versioning
    lockfiles
    scripts

14. Semantic versioning
  Format
    major.minor.patch

  Meaning
    major -> breaking changes
    minor -> backward-compatible features
    patch -> backward-compatible fixes

15. Environment variables
  Node apps commonly use environment variables for:
    secrets
    database URLs
    API keys
    environment-specific config

  Important security point
    Do not hardcode secrets in source code.

16. Core modules you should know
  `fs`
    file system operations

  `path`
    file path manipulation

  `http`
    raw HTTP server creation

  `url`
    URL parsing

  `events`
    event emitter pattern

  `stream`
    streaming data

  `process`
    runtime process information and environment

17. fs module
  Used for reading, writing, updating, and deleting files.

  Important interview point
    Prefer async fs APIs in server applications to avoid blocking.

18. Streams
  Streams let you process data chunk by chunk instead of loading everything into memory at once.

  Why this matters
    Better memory efficiency
    important for large files, uploads, downloads, and transformations

  Types of streams
    readable
    writable
    duplex
    transform

19. Buffers
  Buffers represent raw binary data.
  They matter in file handling, streams, networking, and low-level data manipulation.

20. HTTP server basics
  Node can create raw HTTP servers.
  Frameworks like Express sit on top of this and simplify routing and middleware.

  Important point
    Understanding raw HTTP basics helps you understand what frameworks are abstracting.

21. Async programming in Node
  You should know:
    callbacks
    promises
    async/await

  Best practice answer
    Prefer async/await for readability, but still understand promises and callback-based APIs because they appear in real systems and interviews.

22. Error handling in async code
  Important patterns
    try/catch with async/await
    `.catch()` with promises
    centralized error handling in API frameworks

  Common mistake
    forgetting to handle rejected promises

23. EventEmitter
  Node has an event emitter pattern for pub-sub style behavior.

  Why interviewers ask
    It shows whether you understand Node’s event-driven model beyond just HTTP APIs.

24. Process object
  `process` gives access to:
    environment variables
    argv
    process ID
    exit codes
    runtime info

25. Thread pool and libuv
  Node uses libuv for async I/O handling.
  Some operations like file system work and crypto use the libuv thread pool.

  Good interview point
    Not all async work is "magic"; some of it is handled via background threads managed by libuv.

26. Worker threads
  Worker threads help with CPU-heavy tasks by moving work off the main thread.

  Use cases
    image processing
    heavy parsing
    CPU-heavy computation

27. Cluster vs worker threads
  Cluster
    multiple Node processes
    used to use multiple CPU cores for serving requests

  Worker threads
    multiple threads within a process
    better for CPU-heavy tasks

28. Node performance basics
  Important topics
    avoid blocking the event loop
    use async APIs
    stream large data
    cache wisely
    paginate large queries
    measure before optimizing

29. Common Node interview question
  What blocks the event loop?

  Good answer
    CPU-heavy JavaScript work, synchronous file system operations, infinite loops, and poorly designed heavy computation on the main thread can block the event loop.

30. Memory leaks in Node
  Common causes
    global references
    event listeners not cleaned up
    timers not cleared
    large in-memory caches without limits

31. API design basics in Node backends
  Even if Express or another framework is used, interviewers often care about:
    route design
    input validation
    auth
    error handling
    consistent responses
    separation between route handlers, business logic, and data access

32. Backend layering
  Good structure often looks like:
    route/controller layer
    service/business logic layer
    data access layer

  Why this matters
    It improves maintainability, testability, and separation of concerns.

33. Logging
  Good logging should help debug production issues without leaking secrets.

  Bad logging
    passwords
    tokens
    secret values

34. Security basics in Node apps
  You should know:
    input validation
    auth and authorization
    environment secret management
    SQL injection awareness
    XSS awareness
    secure headers
    rate limiting

35. Node interview traps
  Be careful with these
    saying Node is multithreaded in the same way as Java
    saying async means parallel CPU execution automatically
    ignoring event loop blocking
    not knowing the difference between promises and async/await
    not understanding streams

36. React vs Node quick contrast
  React
    UI library
    runs primarily in browser environments
    component and rendering focused

  Node.js
    runtime
    often used for servers and tooling
    event loop and I/O focused

39. Short React speaking answer
  "React is a declarative, component-based UI library. Its main value is that UI becomes a function of state. I think about React in terms of components, props, state, rerenders, and controlled data flow. For interviews, I focus a lot on state management, hooks, rendering behavior, and performance tradeoffs."

40. Short Node speaking answer
  "Node.js is a JavaScript runtime designed around non-blocking I/O and the event loop. It is especially strong for APIs and network-heavy applications. For interviews, I focus on the event loop, async programming, core modules, backend structure, and performance tradeoffs around blocking vs non-blocking work."
