Must Know First

1. What is this landing page doing in product terms?
  Simple answer
    The landing page is the product entry point. It introduces GitLog AI, explains the core flow, and pushes the user to the next action. If the user is not logged in, the main CTA takes them to login. If the user is already logged in, it sends them straight to the dashboard. So it is not just marketing UI, it is also a smart entry layer into the app.

2. Server Component vs Client Component in very simple words
  Simple answer
    A Server Component runs on the server and is good for fetching data, reading cookies, and rendering the initial UI without sending extra JavaScript to the browser.
    A Client Component runs in the browser and is needed when I use state, effects, event handlers, browser APIs, or interactive auth actions.

  In GitLog AI
    The home page and navbar are server-rendered because they read auth state and decide what to show initially.
    The login page and user menu are client-side because they need click handlers, local state, router navigation, and browser auth actions.

3. Why Next.js fits this project better than plain React plus a separate Node app
  Must know deeply
    This is one of the highest-value answers for your project.

  Good answer
    I used Next.js because GitLog AI is a full-stack product, not just a frontend. I needed routing, server-side rendering, API routes, middleware, metadata, image optimization, and auth-aware rendering in one framework.
    If I had used React and Node separately, I would have had to build and maintain the frontend app, backend app, SSR setup, routing strategy, and deployment integration separately.
    In Next.js App Router, I can keep pages, layouts, API routes, and server-side logic in one codebase. That makes it faster to build and easier to reason about for a project like this.

  Balanced answer
    React plus Node is still a valid choice when the frontend and backend need to scale separately, or when the backend is a large independent service. But for GitLog AI, where UI, auth, GitHub integration, and generation flow are tightly connected, Next.js gave me better full-stack productivity and simpler architecture.

4. Why auth affects even a simple-looking landing page
  Simple answer
    Because the landing page is part of the user journey. If the user is already authenticated, showing a login button again is unnecessary friction. It is better UX to show "Go to Dashboard" immediately. That means the page needs to know session state before rendering.

5. What middleware is doing in one sentence
  Simple answer
    Middleware is intercepting the request early, refreshing the session when needed, and redirecting users away from routes they should not access.

Interview Questions and Answer Briefs

Section 1: Product and architecture understanding

1. Walk me through the landing page of your project as if I am seeing the app for the first time.
  Answer Brief
    The landing page introduces the product, explains the flow in a simple way, and gives a clear CTA. In GitLog AI, the CTA is auth-aware. If the user is logged in, I send them to the dashboard. If not, I send them to GitHub login. I also keep the navbar and footer shared across the app through the root layout, so the experience feels consistent from the first page onward.

  In this project
    The flow is mainly driven by app/page.tsx, app/layout.tsx, components/Hero.tsx, and components/Navbar.tsx.

2. What makes this landing page more than just static UI?
  Answer Brief
    The interesting part is that it is user-aware. It checks session state and changes the main action based on whether the user is authenticated. That means the page is connected to auth and layout behavior, not just design. It is also part of the full product flow, not a disconnected brochure page.

3. Why did you keep the navbar and footer in a shared layout?
  Answer Brief
    I wanted consistent navigation across the app. In Next.js App Router, the root layout is the clean place to put shared UI like navbar and footer. It reduces duplication and keeps the app shell consistent. The tradeoff is that if the navbar has server-side logic like auth checks, that cost now affects every route using that layout.

4. If I ask you to explain the landing page architecture in one minute, what would you say?
  Answer Brief
    I would say the landing page is built using Next.js App Router. The home page is server-rendered and reads auth state. The root layout wraps all pages with a shared navbar and footer. The hero section is presentational, but its CTA depends on whether the user is logged in. Login and logout interactions are handled in client-side components, while session-aware rendering is done on the server. Middleware protects private routes and helps maintain session continuity.

5. What are the main tradeoffs in your landing page architecture?
  Answer Brief
    The main benefit is good UX and simple full-stack integration. The main tradeoff is that the page is less cache-friendly because it depends on user session state. Also, shared auth-aware layout logic can create duplicate session reads if not designed carefully. So the architecture is practical, but there is room to optimize if traffic or complexity grows.

Section 2: Next.js App Router

6. What does the App Router give you in this module?
  Answer Brief
    It gives me file-based routing, layouts, server components by default, route grouping, metadata support, and easy colocation of UI with server logic. For the landing module, App Router helps me keep the page, layout, navigation, and auth-aware rendering in one clean structure.

7. How is App Router different from the older Pages Router in the way you think about this page?
  Answer Brief
    In App Router, server components are the default, layouts are first-class, and data fetching can happen directly inside server components. That changes how I think about page design. Instead of fetching everything on the client and hydrating a big page, I can render useful UI on the server first and only make specific pieces interactive when needed.

8. Why is it useful that Server Components are the default in your project?
  Must know deeply
    This is another high-value topic.

  Good answer
    Because a lot of my app is data-aware, but not necessarily interactive. For example, the landing page and navbar need to know if the user is logged in, but they do not need local browser state for that. If I keep them as Server Components, I can read cookies and auth state directly on the server and send less JavaScript to the browser. That improves initial load and keeps the client bundle smaller.

  The point you should make
    Not every component that shows dynamic data needs to be a Client Component. It only needs to be client-side if it truly needs browser-only behavior.

9. What would force a component to become a Client Component?
  Answer Brief
    If I need useState, useEffect, browser APIs, click handlers that depend on client runtime, or client-side auth actions, then it needs "use client". In my project, login and user-menu behavior need that. But purely presentational components or server-rendered auth-aware components do not.

10. How would you explain the difference between rendering on the server and hydrating in the browser?
  Answer Brief
    Server rendering means the server prepares the HTML before the browser receives it. Hydration means React attaches client-side behavior to the already-rendered UI in the browser. In my project, I use server rendering to show the correct initial UI, and hydration only where interaction is needed.

11. What is a hydration mismatch, and why should you care?
  Answer Brief
    A hydration mismatch happens when the HTML generated on the server does not match what React expects on the client during hydration. That can create warnings and unpredictable UI behavior. I care about it because auth-aware and time-based UI can accidentally cause different output between server and client if not handled carefully.

  Safer beginner explanation
    The server and browser should agree on what the page looks like at first render.

12. Is your landing page static or dynamic?
  Answer Brief
    It is dynamic in practice because the output changes based on user session state. If there were no auth checks and no user-specific decisions, it could be more static. But in my implementation, the CTA and navbar behavior depend on whether the user is logged in.

13. If an interviewer asks about caching for this page, what is a safe answer?
  Answer Brief
    I would say I have to be careful with caching because the page is auth-aware. A fully static cached page would not work well if I want personalized CTA behavior. One practical improvement could be keeping most of the marketing content static and isolating only the auth-aware piece, but in my current project the page is rendered dynamically for simplicity and correctness.

Section 3: React concepts through this module

14. How do you decide what should stay presentational and what should contain logic?
  Answer Brief
    I try to keep components presentational if they are mainly about structure and styling, and move logic closer to the place where data or state is actually needed. For example, the hero is mostly presentational. It just receives whether a user exists and renders the appropriate CTA. I do not push login logic into it unnecessarily.

15. Why is prop-driven UI better than letting every component fetch on its own?
  Answer Brief
    Prop-driven UI keeps components simpler, easier to test, and easier to reason about. If every component fetched separately, it would increase duplication and make data flow harder to follow. Passing simple data like a user boolean into the hero is cleaner.

16. Where do React hooks naturally belong in this module?
  Answer Brief
    Hooks belong in interactive client components. In this module, they make sense in places like the login page for loading state and the user menu for open-close behavior and logout flow. They do not belong in purely server-rendered parts like the page component or navbar when those are only reading server-side auth state.

17. What would you say if asked whether you overused Client Components?
  Answer Brief
    I would say no. I used Client Components only where interactivity actually required them, like login and the user dropdown. For auth-aware rendering of the initial UI, I kept it on the server. That is one of the main benefits of using App Router correctly.

Section 4: Authentication and session-aware rendering

18. How does auth show up in your landing page flow?
  Must know deeply
    This is one of the most important answers for your project.

  Good answer
    Auth affects the first page in two ways. First, it changes the CTA and navbar options depending on whether the user has a valid session. Second, middleware protects private routes like the dashboard and generation pages, so unauthorized users are redirected before they can access them.
    In GitLog AI, login is done through GitHub OAuth using Supabase Auth. The landing page itself does not perform login, but it is aware of session state and routes the user correctly into the next step.

  Good structure for speaking
    I read session state on the server.
    I render the correct action for the user.
    I use middleware to protect the rest of the flow.
    I keep actual login and logout actions in client-side components.

19. Why not just fetch auth state on the client after page load?
  Answer Brief
    That would work, but it gives a worse initial experience. The user could briefly see the wrong CTA and then see it change after hydration. Server-side auth-aware rendering avoids that flicker and makes the first render more correct.

20. What is the role of Supabase SSR in this module?
  Answer Brief
    Supabase SSR helps me create a server-side client that can read auth cookies during rendering. That is what lets server components know the user state. Without that, I would be much more dependent on client-side checks.

21. What is the role of middleware in this project?
  Answer Brief
    Middleware handles request-time auth control. It checks session state early, refreshes session cookies when needed, and redirects users away from routes they should not access. This is important because private pages like dashboard and generator should not rely only on client-side protection.

22. What is the difference between showing auth-aware UI and protecting a route?
  Answer Brief
    Showing auth-aware UI means changing what the user sees based on session state, like showing "Go to Dashboard" instead of "Login". Protecting a route means blocking access completely if the user is not allowed to be there. UI logic is about experience. Route protection is about security and control flow.

23. Why is logout handled on the client?
  Answer Brief
    Because logout is a user interaction that starts from a button click in the browser. The component needs click handling, client navigation, and a browser-side Supabase client to sign out and update the UI immediately.

Section 5: Next.js vs React + Node discussion

24. If I asked, "Could you have built this with React frontend plus Express backend?", what would you say?
  Answer Brief
    Yes, definitely. The project could work that way. But Next.js gave me a simpler full-stack setup. I could keep pages, layouts, API routes, middleware, and server-side rendering in one codebase. That was a better fit for a project where frontend and backend are tightly connected and the team size is small.

25. When would React plus Node be the better answer?
  Answer Brief
    It can be better when the backend is a large independent service, when frontend and backend teams are fully separated, or when you need a very customized backend architecture. For my project, the integration points were close enough that Next.js reduced complexity.

26. How would you answer if the interviewer tries to compare them aggressively?
  Answer Brief
    I would avoid saying one is always better. I would say the right choice depends on the product, team structure, scaling needs, and deployment model. For GitLog AI, I chose Next.js because it gave me faster full-stack development and better colocation. In another system, especially a larger backend-heavy one, React plus Node could be the better architecture.

Section 6: Performance and frontend quality

27. What are the most practical frontend performance concerns for this module?
  Answer Brief
    The first is sending unnecessary client JavaScript. That is why I keep non-interactive parts on the server. The second is large image assets on the hero section. The third is repeated auth/session checks across shared layout and page code. The fourth is making sure the first screen renders cleanly without flicker.

28. How does Next Image help you here?
  Answer Brief
    Next Image helps optimize images by controlling sizing and delivery more intelligently than raw img tags. In my project, it is used for hero assets and user avatars. For remote avatars, I also have to allow the external image domain in Next config.

29. What would you improve next if performance became a concern?
  Answer Brief
    I would first reduce duplicate session reads if they are happening in both page and shared navbar logic. Then I would check image sizes and loading behavior. After that, I would look at font loading, bundle size from client components, and whether I can separate static marketing content from the auth-aware part more cleanly.

30. Is the landing page a good place to think about Core Web Vitals?
  Answer Brief
    Yes. It is the first screen of the product, so performance and visual stability matter a lot. Fast first render, stable layout, good image handling, and not shipping unnecessary client-side JavaScript all help here.

31. What is one thing you would say about responsive design in this module?
  Answer Brief
    The landing page should work cleanly across mobile and desktop because it is the first touchpoint for users. I would mention that I used responsive utility classes and flexible layout patterns so the hero, CTA, navbar spacing, and content blocks adapt across screen sizes.

Section 7: Styling, design, and UI choices

32. How would you explain your styling approach on this page?
  Answer Brief
    I used Tailwind CSS for component-level styling because it lets me move quickly and keep styles close to the component. I also kept a small amount of shared global CSS for app-wide defaults and a few shared style concerns.

33. When should you use global CSS and when should you avoid it?
  Answer Brief
    Global CSS is good for resets, base typography, root variables, and truly shared styles. I avoid putting too much component-specific styling there because it makes maintenance harder and creates hidden coupling between components.

34. How would you discuss design consistency without sounding like only a UI person?
  Answer Brief
    I would say consistency matters because it reduces cognitive load for the user and also makes the codebase easier to scale. Shared layout, repeatable button styling, and a clear visual system are not just design decisions, they are maintainability decisions too.

35. What UI weaknesses would you admit honestly in this module?
  Answer Brief
    I would say there is room to improve polish. For example, stronger typography choices, better content depth on the landing page, real footer links, and better semantic text for some images would make the module more production-ready.

Section 8: Accessibility and SEO

36. What accessibility basics would you mention for this page?
  Must know deeply
    This topic is common and easy to score well on if you stay practical.

  Good answer
    I would check semantic structure, keyboard accessibility, focus states, button and link correctness, meaningful alt text, and color contrast. For a landing page, I also care that the main CTA is clearly understandable and reachable with keyboard navigation.

  Strong beginner-friendly wording
    Accessibility is not only for compliance. It usually improves overall usability too.

37. Give me one example of accessibility thinking from your project.
  Answer Brief
    A simple example is making sure navigation actions are actual links when the user is navigating to another page, and actual buttons when triggering an action. Another example is making sure loading and disabled states are visible on the login action.

38. What SEO basics matter for the landing page of a product like this?
  Answer Brief
    Metadata, title, description, social preview tags, semantic headings, and clean content structure matter. For a product landing page, I would also care about descriptive copy that makes the product and use case clear. In my project, I set metadata and Open Graph basics, but there is room for deeper SEO improvement.

39. Why do metadata and Open Graph tags matter even in a technical project?
  Answer Brief
    Because they affect how the product looks when shared and how clearly it is understood by search engines and users. Even developer tools benefit from strong previews and clear metadata because discovery and first impression still matter.

Section 9: TypeScript

40. Where does TypeScript help in a landing page module that looks simple?
  Answer Brief
    It helps define props clearly, prevents simple mistakes, and makes component contracts easier to understand. Even if the UI is simple, TypeScript still improves safety and readability. In this module, it is useful for prop typing, children typing in layout, and third-party types like authenticated user objects.

41. What type mistakes are common in beginner frontend code?
  Answer Brief
    Overusing any, not handling undefined or null properly, weak prop typing, and mixing server-side assumptions with browser-side assumptions. I try to keep props explicit and handle optional values carefully, especially around auth data.

42. If I ask you whether interfaces or type aliases are better, how do you answer?
  Answer Brief
    I would say both are useful and I choose based on readability and use case. For straightforward component props, either can work. The important thing is consistency and clarity, not treating one as universally better.

Section 10: Testing, debugging, and improvement mindset

43. How would you test this landing page module?
  Answer Brief
    I would test the main user flows:
    unauthenticated user sees login CTA
    authenticated user sees dashboard-oriented CTA
    login action shows loading state
    protected routes redirect correctly
    navbar changes correctly based on session state
    responsive layout works on smaller screens

44. What bugs are realistic in this module?
  Answer Brief
    Wrong CTA due to stale auth state, hydration mismatch between server and client, broken redirect flow, missing avatar domain config, layout overlap issues on mobile, and placeholder links or weak accessibility details slipping into production.

45. What is one debugging approach you would use if users said the CTA is sometimes wrong?
  Answer Brief
    I would verify where auth state is being read, whether the session is refreshed correctly, whether middleware is behaving consistently, and whether the server-rendered UI and client state are out of sync. I would trace the flow from request to render instead of only checking the button component.

46. If you had one more day to improve this module, what would you do?
  Answer Brief
    I would improve polish and architecture together. I would clean up duplicate session reads, strengthen accessibility details, make the footer production-ready, improve typography and content quality, and review whether the landing page can be made more cache-friendly without losing auth-aware behavior.

Section 11: Node.js and backend relevance from a frontend-looking module

47. Does Node.js event loop discussion matter for the landing page?
  Answer Brief
    It matters a little, but not as much as in heavy API routes. The landing page mostly does I/O-bound work like reading auth state and rendering. That fits well with the Node model. The bigger event loop discussion in this project comes later in API routes that fetch GitHub data and call AI providers.

48. If an interviewer asks Node questions here, what is a safe way to connect them back to your project?
  Answer Brief
    I would say this module itself is mostly about rendering and auth-aware request handling, but it still sits in the same Next.js runtime where async I/O matters. Then I would connect Node more strongly to the repo-fetch, commit-fetch, and changelog generation modules where async external calls are more central.

Section 12: Strong closing answers

49. What would you say is the best engineering decision in this module?
  Answer Brief
    Keeping the initial UI auth-aware on the server while limiting Client Components only to true interactivity. That gave me a better user experience and kept the architecture cleaner.

50. What would you say is the weakest part of this module today?
  Answer Brief
    The module works well functionally, but it can be improved in polish and optimization. The biggest improvement areas are reducing duplicated auth reads, improving some accessibility details, and making the landing experience feel more production-complete from a content and branding perspective.

51. What should you absolutely not say in an interview about this module?
  Answer Brief
    Do not say:
      "Everything is client-side."
      "Next.js is always better than React plus Node."
      "Server Components are just for SEO."
      "Middleware and UI checks are basically the same thing."
      "Accessibility is mainly about screen readers only."
    These answers sound shallow and hurt credibility.

High-value answers you should be able to speak smoothly

1. Why Next.js for this project
  Strong study answer
    I chose Next.js because GitLog AI needed both frontend and backend features in one product. I wanted server-rendered pages, layouts, auth-aware rendering, API routes, middleware, and easy deployment. Next.js App Router gave me all of that in one framework. It reduced architectural overhead compared to building React and Node separately for a project where the frontend and backend are tightly coupled.

2. Why Server Components and Client Components both exist in your app
  Strong study answer
    I use Server Components for initial rendering and auth-aware UI because they can read server-side data without sending unnecessary JavaScript to the browser. I use Client Components only when I need browser-side interactivity, like login clicks, menu toggling, logout, or router actions. That split gives me better performance and cleaner responsibility boundaries.

3. How auth affects the landing page
  Strong study answer
    The landing page is not just branding, it is the first decision point in the product flow. So it needs to know whether the user is logged in. If the user is authenticated, I take them toward the dashboard. If not, I push them into login. This improves UX and reduces friction. Middleware separately protects private routes, so the landing page improves flow while middleware enforces access.

4. How you would compare Next.js and React plus Node in a mature way
  Strong study answer
    I would not say one is universally better. For GitLog AI, Next.js was the better fit because I needed full-stack colocation, auth-aware SSR, API routes, middleware, and fast iteration. If I were building a larger system with a strongly independent backend, multiple clients, or team separation between frontend and backend, React plus Node could be a stronger architecture.
