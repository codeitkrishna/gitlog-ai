Must Know First

1. What does this module do in product terms?
  Simple answer
    This module takes a reviewed commit set and turns it into a structured changelog using an LLM. The result is not just plain text. It is categorized output that the UI can render as Features, Bug Fixes, Improvements, Breaking Changes, and Chore items.

2. What is the technical flow in one short explanation?
  Simple answer
    The frontend sends the selected commits, repository information, and desired tone to the generate API. The backend validates the request, checks rate limits, builds a structured prompt, sends it to the configured AI provider, parses the returned JSON, validates the structure, and sends the typed changelog back to the frontend with metadata.

3. What is the most important idea in this module?
  Must know deeply
    The most important idea is that the route does not trust the AI output blindly.

  Good answer
    The route validates the request before generation.
    It builds a structured prompt with explicit output rules.
    It uses retries and fallback providers for resilience.
    It parses the AI response carefully.
    It validates that the JSON matches the expected changelog structure.
    So the module treats AI as an unreliable external system that needs guardrails, not as a perfectly deterministic function.

4. Why is this module important in interviews?
  Simple answer
    Because it shows practical AI engineering, not just "I called an API." It includes validation, prompt design, provider abstraction, retry logic, fallback behavior, rate limiting, response parsing, and user-facing error handling.

Section 1: Product and architecture understanding

1. Walk me through the changelog-generation flow in your project.
  Answer Brief
    After the user fetches commits and reviews them, the frontend sends the selected commit list, repository info, and tone to the generate API. The API checks that the user is authenticated, applies a per-user rate limit, validates the tone and commit payload, builds a prompt, calls the AI layer, parses the model response into structured JSON, validates the final shape, and returns the changelog with metadata like generation time and commit count.

2. Why did you separate commit fetching from changelog generation?
  Must know deeply
    This is one of the strongest product answers in the whole project.

  Good answer
    Because generation is more expensive, slower, and less predictable than fetching commit data. I wanted users to first verify that the commit history is correct, and only then run the AI step. That improves trust, reduces wasted generation attempts, and makes the workflow feel more transparent.

3. Why does the frontend send commits to `/api/generate` instead of having the backend refetch them?
  Answer Brief
    Because the user has already reviewed and filtered the commit set on the client side. Sending that exact selected set to generation ensures the AI works on the same input the user saw, instead of refetching and potentially producing a mismatch.

4. Why is this a good full-stack design point?
  Answer Brief
    Because it shows that the frontend and backend are coordinating around a clear contract. The frontend owns selection and review, while the backend owns generation, validation, and provider communication.

Section 2: Request validation and API discipline

5. What does the generate API validate before calling the AI?
  Answer Brief
    It validates authentication, rate limiting, tone validity, commit array presence, maximum commit count, repository identity information, and the shape of each commit object. That means invalid or incomplete requests are stopped before they reach the AI provider.

6. Why validate the commit payload if those commits already came from your own UI?
  Answer Brief
    Because the API should not assume the caller is always the trusted UI. Requests can be sent directly, so the backend should verify the structure it depends on.

7. Why validate tone values strictly?
  Answer Brief
    Because tone directly affects prompt behavior and output style. Restricting it to a known set keeps the system predictable and avoids accidental or invalid prompt states.

8. Why is there also a commit-count cap in generation if commit fetching already has a 500 cap?
  Must know deeply
    This is a good layered-validation answer.

  Good answer
    Because generation has its own resource constraints. Even if the commit-fetch module can return up to 500 commits, sending too much data to the AI can make prompts too large, slow, or expensive. The generation module therefore enforces its own max request size and also slices the prompt further inside prompt construction.

9. Why resolve `repoName` from either `repoName` or `owner + repo`?
  Answer Brief
    Because it makes the route more flexible while still keeping a clear repository identity for the prompt and metadata. It accepts slightly different input shapes without losing consistency.

10. Why is `normalizeCommits` useful?
  Answer Brief
    It ensures the generation pipeline works with a clean, predictable internal commit shape. That is useful before building prompts or doing any further processing.

Section 3: Rate limiting and product protection

11. Why did you add rate limiting to changelog generation?
  Must know deeply
    This is an important answer because it shows practical backend thinking.

  Good answer
    AI generation is expensive and abuse-prone compared to normal data fetches. I added a per-user rate limit so one user cannot spam the generation route excessively. In my current implementation, users can generate up to 10 changelogs per hour.

12. Why is rate limiting especially important for AI endpoints?
  Answer Brief
    Because AI calls are slower, costlier, and easier to abuse than many regular API routes. Without limits, a single user or script could create unnecessary cost and system pressure quickly.

13. How does your current rate limit work?
  Answer Brief
    It checks a Supabase table that records recent generation requests for the current user and counts how many happened within the last hour. If the count is too high, the route returns a 429 response with a friendly message.

14. What is good about this rate-limit design?
  Answer Brief
    It is easy to understand, per-user, and uses the database to make the limit persistent across requests instead of relying only on in-memory counters.

15. What are the weaknesses of this current approach?
  Answer Brief
    It is simple, but not very advanced. It does not account for prompt size or token usage, and it depends on database writes after successful requests. A more mature design might consider sliding windows, cost-based limits, or provider-usage metrics.

Section 4: Prompt engineering

16. What is the purpose of the prompt builder in your project?
  Answer Brief
    The prompt builder converts commit data, tone, and repository context into a structured instruction set for the model. Its job is to reduce ambiguity and push the model toward useful, human-like changelog output in a consistent JSON format.

17. Why not hardcode the prompt directly inside the API route?
  Answer Brief
    Because prompt construction is its own concern. Keeping it separate improves readability, maintainability, and makes it easier to evolve prompt logic without cluttering the route handler.

18. What kind of instructions does your prompt include?
  Must know deeply
    This is a very strong AI-engineering answer.

  Good answer
    The prompt includes repository context, commit summaries, selected tone, category definitions, classification rules, grouping rules, examples of good and bad phrasing, style instructions, and an explicit required JSON output schema. It is not just "summarize these commits." It tries to shape both content quality and response structure.

19. Why include tone-specific rules?
  Answer Brief
    Because the same raw change can be described differently depending on the audience. Developers, end users, and marketing or stakeholder readers care about different levels of detail and different language styles.

20. Why include examples of good and bad changelog phrasing?
  Answer Brief
    Because examples help the model understand the difference between vague generic output and concrete useful output. This usually improves response quality more than abstract rules alone.

21. Why include strict JSON output instructions?
  Answer Brief
    Because the frontend expects structured data, not free-form prose. Clear output instructions make parsing easier and reduce the chance of unusable responses.

22. Why do you only send a limited number of commits into the prompt?
  Must know deeply
    This is a strong practical AI-system answer.

  Good answer
    Because prompt size affects cost, latency, and model reliability. Even though the fetch module can return more commits, the prompt builder only analyzes a limited subset to keep the generation practical. This is a tradeoff between completeness and system efficiency.

23. What is the tradeoff of slicing commits for the AI prompt?
  Answer Brief
    It makes generation faster and safer, but it also means the AI may not see the full commit set when the range is large. That is acceptable for the current product scope, but it is an important tradeoff to understand and explain honestly.

24. Why is prompt engineering a real engineering task here and not just wording?
  Answer Brief
    Because the prompt directly affects correctness, consistency, parseability, cost, and user trust. In this module, prompt design is part of system behavior, not just copywriting.

Section 5: AI provider abstraction

25. Why did you put provider logic into a separate AI layer?
  Answer Brief
    Because I did not want the route handler to know the details of Gemini and Anthropic APIs. A dedicated AI layer gives me a cleaner abstraction for provider selection, retries, fallback, and error normalization.

26. Which AI providers does your project support?
  Answer Brief
    The project supports Gemini and Anthropic. The AI layer can choose one based on configuration and fall back to the other when appropriate.

27. Why support multiple providers instead of just one?
  Must know deeply
    This is one of the strongest answers in this module.

  Good answer
    Because provider availability, quota, latency, and reliability can vary. Supporting multiple providers gives the system better resilience. If one provider is down, rate-limited, or misconfigured, the app has a chance to recover by falling back to the other provider instead of failing immediately.

28. How do you choose provider order?
  Answer Brief
    The AI layer checks configuration and available API keys. It respects an explicit preferred provider if one is set, but it also builds a fallback order if both providers are available.

29. Why is that a better design than hardcoding one provider?
  Answer Brief
    Because it keeps the system configurable and more robust. It also makes testing and future provider changes easier.

Section 6: Retries and fallback behavior

30. Why did you add retries around provider calls?
  Must know deeply
    This is an important reliability answer.

  Good answer
    Because some AI failures are transient, like temporary network problems or short-term provider instability. Retrying with exponential backoff gives those requests a chance to succeed without immediately failing the user.

31. What is exponential backoff in simple words?
  Answer Brief
    It means waiting a little longer between each retry attempt, for example 1 second, then 2 seconds, then 4 seconds. This reduces pressure on the external service and gives transient failures time to recover.

32. Why not retry every error?
  Answer Brief
    Because some failures are not transient. For example, invalid API keys or bad requests will not succeed just by retrying. Retrying those would only waste time and resources.

33. What kinds of errors are considered retryable in your AI layer?
  Answer Brief
    Transient provider errors like server-side failures, some rate-limit or network-like issues, and fetch or timeout style problems are retryable. Authentication and obvious bad-input errors are not.

34. Why is fallback separate from retry?
  Answer Brief
    Retry means trying the same provider again because the failure may be temporary. Fallback means moving to another provider because the current one may be unavailable, rate-limited, or misconfigured. They solve different reliability problems.

35. When does your system attempt provider fallback?
  Answer Brief
    It attempts fallback when the current provider fails in a way that still makes another provider worth trying, such as certain rate-limit, auth, or provider-side availability scenarios, and when another provider is actually configured.

36. Why is this a good interview topic?
  Answer Brief
    Because it shows practical resilience design. You are not just integrating an API, you are designing around real-world external-system unreliability.

Section 7: Parsing and validation of AI output

37. Why do you need a parser for AI responses?
  Must know deeply
    This is one of the strongest AI-backend answers in the project.

  Good answer
    Because AI output is not guaranteed to be perfectly formatted even when the prompt requests JSON. The parser extracts the likely JSON content, tries to parse it, and validates the final structure before the rest of the app trusts it.

38. What does your parser handle besides plain JSON?
  Answer Brief
    It can handle responses where the model wraps JSON in code fences, and it can also try to extract the object content by finding the first and last braces if the response includes surrounding text.

39. Why is structure validation important after `JSON.parse` succeeds?
  Answer Brief
    Because valid JSON can still be the wrong shape. The frontend expects a specific changelog schema, so the parser also verifies that categories are arrays and that each entry includes a valid title, description, and commit string array.

40. Why return an empty changelog structure for missing categories instead of failing?
  Answer Brief
    Because empty categories are a valid business outcome. If the model omits a category because there are no entries, the system can safely treat that as an empty array rather than as a hard failure.

41. What is one good thing about deduplicating commit SHAs in parsed entries?
  Answer Brief
    It keeps the output cleaner and prevents redundant commit references if the model repeats the same SHA in one entry.

42. What kind of errors from parsing are mapped specially in the route?
  Answer Brief
    Parse or schema-style issues that indicate the AI returned invalid JSON content or an invalid structure are treated more like upstream provider failures and can map to a 502-style response instead of a generic 500.

43. Why is that a smart design choice?
  Answer Brief
    Because it helps distinguish between "my server crashed" and "the upstream model returned unusable output." That distinction is useful for debugging and for thinking about reliability.

Section 8: Error handling and user-facing reliability

44. How does your generation module handle provider-specific errors?
  Answer Brief
    The AI layer normalizes provider-specific errors into clearer application-level messages, such as invalid API key, temporary unavailability, or rate-limit situations. That gives the rest of the app a more consistent error surface.

45. Why normalize provider errors?
  Answer Brief
    Because different providers expose different error formats, statuses, and wording. Normalization makes the behavior more consistent for the route and for the user experience.

46. What kinds of generation failures are most realistic in your project?
  Answer Brief
    Invalid provider credentials, rate limiting, temporary provider outages, network issues, prompt-size pressure, and AI responses that are syntactically or structurally invalid.

47. Why is graceful AI failure important?
  Answer Brief
    Because users will trust the feature more if failures are clear and recoverable. AI systems are inherently less deterministic than normal CRUD APIs, so good failure handling matters more here.

48. What is one honest weakness you can mention in this module?
  Must know deeply
    This is a strong critique answer.

  Good answer
    One honest weakness is that prompt truncation and commit slicing mean the model may not always see the full history for large ranges. Another is that even with parsing and validation, model output quality is still probabilistic. The module is resilient, but it is not perfectly deterministic, and that is something I would acknowledge clearly in an interview.

Section 9: Product and scaling tradeoffs

49. If an interviewer asks you to critique this module honestly, what would you say?
  Must know deeply
    This is one of the strongest answers in the AI part of the project.

  Good answer
    I would say the module is well structured for a real project because it has validation, retries, fallback providers, rate limiting, and output parsing. But the core tradeoff is that AI quality is still probabilistic and the prompt only includes a limited number of commits. So I would describe it as a practical and resilient generation pipeline, but not something that guarantees perfect semantic accuracy every time.

50. Why is that a strong answer?
  Answer Brief
    Because it shows you understand both engineering quality and the real limits of LLM-based systems. Strong answers do not pretend AI is deterministic when it is not.

51. If generation quality became the top problem, what would you improve first?
  Answer Brief
    I would look at prompt quality, better commit summarization inputs, stronger schema enforcement, maybe per-category validation or repair strategies, and possibly more deliberate handling of large commit sets before they reach the model.

52. If generation cost became the top problem, what would you improve first?
  Answer Brief
    I would review commit slicing, provider choice, prompt compactness, rate limiting strategy, and whether some smaller or cheaper model could handle simpler cases while reserving larger models for more complex histories.

53. Why is this module a good example of "AI as part of a system" rather than "AI as a demo"?
  Answer Brief
    Because the AI call is surrounded by engineering controls: auth, rate limits, request validation, provider abstraction, retry logic, fallback, parsing, schema validation, and metadata. That makes it a proper subsystem rather than a single API call dropped into an app.

Section 10: Testing and debugging

54. How would you test this module?
  Answer Brief
    I would test:
    unauthorized requests
    invalid tone handling
    empty commits handling
    oversized commit payloads
    missing repo identity
    rate-limit behavior
    prompt generation for different tones
    provider retry behavior
    provider fallback behavior
    parsing of clean JSON
    parsing of fenced JSON
    invalid AI output handling
    metadata returned on success

55. If a user says "Commit fetch worked, but changelog generation failed," how would you debug it?
  Must know deeply
    This is a strong practical interview answer.

  Good answer
    I would debug it in layers.
    First, verify the request payload going into `/api/generate`, especially tone, repo information, and commit count.
    Second, check whether rate limiting blocked the request.
    Third, inspect which provider was used and whether retries or fallback were triggered.
    Fourth, check whether the provider returned content at all.
    Fifth, inspect whether parsing failed because the output was not valid JSON or had the wrong shape.
    This layered approach matters because generation failure can come from validation, provider connectivity, provider credentials, provider quota, or invalid model output.

56. What is a realistic bug in prompt-related behavior?
  Answer Brief
    A realistic issue is that the prompt may cause over-grouping or under-grouping of commits, especially when many commits are related but not identical. That is not a code crash, but it is still a product-quality bug.

57. What is a realistic bug in parsing behavior?
  Answer Brief
    A realistic issue is that the model returns mostly valid JSON but adds extra explanatory text or slightly wrong field shapes. The parser helps, but this is exactly the kind of semi-structured output problem AI systems run into.

58. Why is this module a good place to discuss "defensive programming"?
  Answer Brief
    Because the route defends itself at every stage: input validation, rate limiting, provider retries, provider fallback, response parsing, and schema validation. It is a clear example of wrapping an unreliable external dependency in strong application-level guardrails.

Section 11: Strong answers to practice

1. Explain the changelog-generation module in one strong answer
  Strong study answer
    In GitLog AI, the generate route takes a reviewed commit set and turns it into a structured changelog using an LLM. Before calling the model, it validates the request, applies a per-user rate limit, resolves the repository name, and normalizes commit input. Then it builds a detailed prompt with tone rules, classification rules, grouping rules, and an explicit JSON schema. The AI layer can use either Gemini or Anthropic, with retries and fallback for resilience. After generation, the response is parsed and validated so the frontend only receives a trusted changelog structure instead of raw model text.

2. Explain the biggest strength of this module
  Strong study answer
    The biggest strength is that it treats AI like an unreliable external system that needs guardrails. The module does not just call a model and hope for the best. It validates input, limits abuse, structures the prompt, retries transient failures, falls back across providers, and validates output before using it.

3. Explain the biggest tradeoff in this module
  Strong study answer
    The biggest tradeoff is between quality and practicality. Better generation often wants more context, but more context increases cost, latency, and prompt-size risk. My current implementation limits the amount of commit data sent to the model so generation stays practical, even though that means the model may not always see the full history.

4. Explain why parsing and validation are necessary
  Strong study answer
    Parsing and validation are necessary because models do not guarantee perfect structure even when prompted carefully. The frontend depends on a specific changelog schema, so the backend has to extract the likely JSON content, parse it, and validate every category and entry before trusting the result.
